# Формат чипов K24

Сырая запись в пользовательской памяти NTAG21x (без NDEF). Один формат на все типы
чипов: КП, браслеты участников, в будущем номера команд. Источник правды для сервера,
Android и iOS.

## Заголовок (стр. 4)

```
байт 0–2  'K' '2' '4'                 (0x4B 0x32 0x34)
байт 3    packed = version << 4 | type
```

| `type` | Чип                | v1 (`packed`) | v2 (`packed`)                 |
|--------|--------------------|---------------|-------------------------------|
| `0x1`  | КП                 | `0x11`        | — (черновик, см. ниже)        |
| `0x2`  | браслет участника  | `0x12`        | `0x22`                        |
| `0x3`  | номер команды      | —             | — (черновик, см. ниже)        |

Читатель проверяет magic и версию. Запись неизвестной версии или типа он игнорирует и
не перезаписывает (см. «Запись»).

## Браслет участника v1 (`0x12`)

```
стр. 4    'K' '2' '4' 0x12
стр. 5–8  code — 16 случайных байт, выдаёт сервер
```

- Код выдаёт `POST /app/race/<id>/member_tags/bind/` (тело без `code`). Нужна сеть.
- Номер на чипе не хранится: приложение узнаёт его из скачанного пула `member_tags`.
- Пул v1 глобальный (`Tag.race IS NULL`).

КП v1 (`0x11`) устроен так же: 16 случайных байт, выдаёт `POST .../tags/`;
`bid = sha256(code)[:16]` — идентичность КП в легенде.

## Браслет участника v2 (`0x22`)

Выдаётся офлайн: номер и гонка лежат на чипе открыто, `code` судейский телефон считает
сам ключом гонки.

```
стр. 4    'K' '2' '4' 0x22
стр. 5    race_id u16 BE, number u16 BE
стр. 6–8  code = HMAC-SHA256(K_race, 0x22 ‖ uid ‖ race_id u16 BE ‖ number u16 BE)[:12]
```

- `uid` — сырые байты UID чипа (обычно 7), не hex-строка.
- `race_id`, `number` — `1…65535`.
- `0x22` в начале сообщения — разделение доменов: тем же ключом гонки будут подписаны
  чипы других типов, и код одного типа не должен сходиться как код другого. Любой новый
  тип, подписанный `K_race`, обязан начинать сообщение своим байтом `packed`.
- HMAC детерминирован: перезапись и повторная отправка дают те же байты.
- Реализация на сервере: `apps/mobile/crypto.member_code`.

### Тестовый вектор

Одинаковый в сервере, Android и iOS.

```
K_race  000102030405060708090a0b0c0d0e0f101112131415161718191a1b1c1d1e1f
uid     04A1B2C3D4E5F6
race_id 42, number 123
code    deb887a736ce08d1fd704d62
запись  4b323422002a007bdeb887a736ce08d1fd704d62
```

### Ключ гонки

- `K_race` — 32 случайных байта, модель `RaceChipKey` (O2O на гонку).
- Создаётся только в облаке: при первом `GET /app/race/<id>/chip_key/` или командой
  `manage.py ensure_chip_keys`. LAN-сервер получает ключ вместе с копией БД и сам его
  не создаёт (`404`, если ключа нет).
- Ключ получает только судья (права админа гонки). Приложение участника ключа не знает
  и код не проверяет.

### Проверка

Только на сервере, задним числом:

- при загрузке отметок `MarkPresent.code_ok` = True / False / None (нечего проверять);
- отметку не отклоняет: несовпадение видно как ⚠ на странице команды в «Данных
  приложения»;
- 12-байтный код проверяется HMAC, 16-байтный — сравнением с кодом v1 из пула.

Привязка (`POST .../member_tags/bind/` с `code`) записывает `Tag(race, nfc_uid, number)`
в пул гонки; неверный код → `400`.

### Модель угроз

- Защищает от записи участником «я №N» на пустую метку и от переноса записи на метку с
  другим UID.
- Клон с тем же UID (magic-метки) — вне рамок.

## Чтение

- Одна команда `FAST_READ 3A 04 08` — стр. 4–8, 20 байт. v1 и v2 читаются одинаково.
- Если `FAST_READ` не поддержан: `READ 30 04` и `READ 30 08` (каждый отдаёт 4 страницы).
- 24 байта (стр. 4–9) читаются так же одним кадром, если формату понадобится больше места.

## Запись

1. Прочитать текущие страницы. Не писать поверх записи `K24` другого типа или
   неподдерживаемой версии, и поверх нечитаемого чипа.
2. Обнулить заголовок (стр. 4).
3. Записать данные (стр. 5–8).
4. Записать заголовок последним — маркер завершения: прерванная запись не оставит
   валидный заголовок над половиной данных.
5. Прочитать обратно и сравнить.

Страницы не блокируются: браслет можно перезаписать.

## Черновики (не реализовано)

Зарезервировано, чтобы не занять байты и типы под другое.

### Номер команды v2 (`0x23`)

Чип на стартовом номере команды. Судья на старте и финише сканирует номер, потом
браслеты участников — так сервер узнаёт, какие браслеты в какой команде.

```
стр. 4    'K' '2' '4' 0x23
стр. 5    race_id u16 BE, team_id u16 BE
стр. 6–8  code = HMAC-SHA256(K_race, 0x23 ‖ uid ‖ race_id u16 BE ‖ team_id u16 BE)[:12]
```

- `team_id` — `Team.id`, не `start_number` (это свободная строка).
- Привязка на сервере не нужна: `team_id` на чипе, код проверяется по скану.

### КП v2 (`0x21`)

```
стр. 4    'K' '2' '4' 0x21
стр. 5    race_id u16 BE, checkpoint_id u16 BE
стр. 6–8  S_cp = HMAC-SHA256(K_race, 0x21 ‖ race_id u16 BE ‖ checkpoint_id u16 BE)[:12]
```

- Без UID: `S_cp` одинаков на всех чипах одной КП, поэтому новый чип работает без
  обновления легенды и сразу открывает запертую легенду (`HKDF(S_cp)`).
- Цена: копия чипа на другой метке проходит проверку (как и сейчас в v1). Взятие с UID,
  которого нет среди привязанных к КП чипов, можно помечать ⚠.
- Вместо `race_id u16 + checkpoint_id u16` возможен `checkpoint_id u32` — гонку сервер
  знает по КП.
